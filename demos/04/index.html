Case 04 · configuration postmortem

The config changed on Saturday. Which data did it change?

A service account reduces batch size and Monday throughput collapses. The audit question is not only who changed the file. It is which exact outputs were produced under that configuration, and whether the record of what ran is still the record that was signed.

Evidence boundary. Every terminal block on this page was captured by running the command shown against the checked-in reference fixtures with the Makoto core at commit 731c5c9, which adds assurance levels (makoto#5, not yet released). Its verifier output is identical to the pinned release 0e41afb. The verification reports are byte-for-byte the files published under the end-to-end proof. Nothing below was typed by hand.

The problem

Monday morning an alert fires: pipeline throughput dropped sharply over the weekend. The configuration shows a batch size nobody remembers setting. Version control says a service account made the change. Chat search finds nothing. Two hours of cross-referencing later, someone finds that an engineer lowered it to debug a memory error and never reverted it.

A postmortem is only as good as the record it reads. If the record of what an operation did can be edited after the fact, whether to tidy it up or to cover a mistake, the investigation reconstructs a history that never happened.

The runnable fixture tests exactly that. After the reference handoff is signed, the recorded operation of the final step is rewritten. One variant ships the edited statement with its original signature. The other edits the payload in place, leaving the bundle index still claiming the original statement digest.

  3. Put Makoto in the path

    History is re-verified on a schedule, not only when it is first received. A nightly job re-runs the gate over every archived handoff, so an after-the-fact edit is found the next morning instead of in the middle of the next incident.

    The workflow

    # Nightly re-verification of archived handoffs. An edit to the
# recorded history after the fact fails here instead of in the
# middle of the next postmortem.
#
# Copy to .github/workflows/makoto-gate.yml in the repository that
# receives handoffs. Layout it expects:
#   handoffs/<name>/bundle/                  what the sender transferred
#   receiver/policy.json                     receiver-owned trust policy
#   receiver/catalog.json, receiver/resources/  pinned private schemas
#   receiver/expected/<name>.artifact.json   expected final artifact
name: Makoto nightly archive re-verification

on:
  workflow_dispatch:
  schedule:
    - cron: "17 3 * * *"

permissions:
  contents: read

env:
  # Pinned so these fixtures replay identically. Delete this line to
  # evaluate against the runner clock.
  EVALUATION_TIME: "2026-09-16T16:00:00Z"
  # Minimum assurance level to accept. L3 (anchored) is the only level
  # that implies an allow decision; a deny still fails at any level.
  REQUIRED_LEVEL: L3

jobs:
  gate:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        include:
          # The sender publishes manifest and head digests out of band.
          # The receiver pins them here, never inside the bundle.
          - handoff: edited-signed-metadata
            manifest: sha256:68ad42d12c69eccb2ba40b3323eaedde67597ee237d02574c48d9497a1cf914c
            head: sha256:e03d959d1c3b1dc11b6380b08b0adc2635547a36cab5e69049c70630a4ccb932
          - handoff: statement-digest-mismatch
            manifest: sha256:b83a5cd1870b8ce1f2931650611f0a19deed0796c0f262e4632efc17981f695c
            head: sha256:962be71738a0146642d27c87fba3c7338b0f2bb764b113b16867bb4808b11977
    steps:
      - uses: actions/checkout@v4
      # Pin the verifier to an exact core commit, like any dependency.
      # Run it from a checkout: the CLI resolves its core schemas from
      # the repository tree. This commit adds `makoto report level`
      # (makoto-project/makoto#5); move the pin to the merged release.
      - uses: actions/checkout@v4
        with:
          repository: makoto-project/makoto
          ref: 731c5c9e3dc59161bd797de70d1d478115bb4c8c
          path: .makoto-core
          persist-credentials: false
      - uses: astral-sh/setup-uv@v6
      - name: Verify the received bundle
        id: verify
        shell: bash
        env:
          HANDOFF: ${{ matrix.handoff }}
          EXPECTED_MANIFEST: ${{ matrix.manifest }}
          EXPECTED_HEAD: ${{ matrix.head }}
        run: |
          verify() {
            uv run --project .makoto-core makoto verify bundle "handoffs/$HANDOFF/bundle" \
              --policy receiver/policy.json \
              --schema-catalog receiver/catalog.json \
              --expected-manifest "$EXPECTED_MANIFEST" \
              --expected-head "$EXPECTED_HEAD" \
              --expected-artifact "receiver/expected/$HANDOFF.artifact.json" \
              --evaluation-time "$EVALUATION_TIME" "$@"
          }
          status=0
          verify --json > makoto-report.json || status=$?
          verify || true
          uv run --project .makoto-core makoto report level makoto-report.json \
            --require "$REQUIRED_LEVEL" || status=1
          exit "$status"
      - name: Keep the verification report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: makoto-report-${{ matrix.handoff }}
          path: makoto-report.json

  postmortem-index:
    # Runs only when every handoff in the matrix was allowed.
    needs: gate
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Refresh the postmortem evidence index
        run: echo "replace with your existing step"

    Download makoto-gate.yml.

Model configuration as transformation evidence

  1. Bind the config bytes Record the exact configuration artifact or digest used by the operation.
  2. Name the executor Sign the transformation with the workload identity and let receiver policy decide whether that identity was authorized.
  3. Append affected outputs Each output statement references the input data, predecessor statement, operation, and configuration evidence.
  4. Traverse the interval Postmortem analysis can identify outputs produced after the changed config and before the corrected one.

What remains outside Makoto

Change approval, human intent, alerting, and root-cause judgment remain separate systems. Makoto supplies attributable, tamper-evident claims about artifacts; it does not decide whether the configuration was wise.

Concrete postmortem record

BeforeConfiguration artifact A is bound to outputs produced under the earlier settings.
ChangeConfiguration artifact B is committed; the next transformation statement names its digest and authorized workload signer.
Blast radiusTraverse descendants produced after B and before corrective artifact C.
FindingThe report identifies attributable claims and affected bytes without pretending to know whether the human change was justified.

Configuration belongs in the evidence as an exact input artifact, not merely a free-text note or ticket URL. The reference fixture does not yet bind a configuration file as an input; the tamper checks shown above apply unchanged when it does.

What else this handles

  • Feature-flag changes that cause regressions in production.
  • Connection-pool or retry settings modified during on-call firefighting.
  • Infrastructure-as-code drift, where deployed state diverges from the recorded plan.
  • Audits that require a complete, unedited history of configuration changes.

Key insight. Configuration is data too. A signed record makes the postmortem fast, and re-verifying that record makes it honest: an edit to history fails verification instead of becoming the history.
