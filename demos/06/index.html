Case 06 · invisible Unicode

Unchanged bytes can still violate policy.

A source file renders exactly like a safe one, but carries 128 invisible variation selectors that encode hidden content. Its digest is honest and its signature is valid, because the dangerous bytes were present when the producer signed them.

Evidence boundary. Every terminal block on this page was captured by running the command shown against the fixtures checked in beside this page, with the Makoto core at commit 731c5c9, which adds assurance levels (makoto#5, not yet released). Its verifier output is identical to the pinned release 0e41afb. The verification reports are byte-for-byte the published allow and deny fixtures. Hidden characters are shown escaped, never embedded in this page.

The problem

Package-registry campaigns have shipped code whose rendered view and byte view disagree. Variation selectors, characters meant to be invisible, encode instructions that a runtime decoder reconstructs. The code looks normal in every editor and review tool.

Those packages can be signed, their hashes valid, and their reviews passed. Provenance and integrity checks answer "are these the bytes that were vouched for?" and the answer is yes. The question nobody asked was whether the bytes a reviewer approved are the bytes a reviewer saw.

  3. Put Makoto in the path

    A pull request that changes a source handoff runs the render-safety gate. The receiver's policy authorizes origin claims only when they carry a passing scan, so a scan result is not advisory: it decides whether the claim can be authorized at all.

    The workflow

    # Render-safety gate for source files. The receiver policy only
# authorizes origin claims that carry a passing render-safety scan.
#
# Copy to .github/workflows/makoto-gate.yml in the repository that
# receives handoffs. Layout it expects:
#   handoffs/<name>/bundle/                  what the sender transferred
#   receiver/policy.json                     receiver-owned trust policy
#   receiver/catalog.json, receiver/resources/  pinned private schemas
#   receiver/expected/<name>.artifact.json   expected final artifact
name: Makoto render-safety gate

on:
  workflow_dispatch:
  pull_request:
    paths:
      - "handoffs/**"

permissions:
  contents: read

env:
  # Pinned so these fixtures replay identically. Delete this line to
  # evaluate against the runner clock.
  EVALUATION_TIME: "2026-09-16T16:00:00Z"
  # Minimum assurance level to accept. L3 (anchored) is the only level
  # that implies an allow decision; a deny still fails at any level.
  REQUIRED_LEVEL: L3

jobs:
  gate:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        include:
          # The sender publishes manifest and head digests out of band.
          # The receiver pins them here, never inside the bundle.
          - handoff: safe-visible
            manifest: sha256:a1020fcb3d691dbbad9d6567c1d33bea36b96a4b99c6282e8958d59472bdb1f6
            head: sha256:44ca1c22a2fd7f3b58f407509b5a9fd933b57d5749786e3256154f1e3d1b82a3
          - handoff: flagged-invisible
            manifest: sha256:ad9c3c7abc51c1dee1fb3939e9ef23c4345203bd1c96a3f2c5ccdff74737e89e
            head: sha256:6fdf6d7bcbdbf7ed7b1b22d9ccee5e9cb1a09bb16ffa884edf30f409310ec274
    steps:
      - uses: actions/checkout@v4
      # Pin the verifier to an exact core commit, like any dependency.
      # Run it from a checkout: the CLI resolves its core schemas from
      # the repository tree. This commit adds `makoto report level`
      # (makoto-project/makoto#5); move the pin to the merged release.
      - uses: actions/checkout@v4
        with:
          repository: makoto-project/makoto
          ref: 731c5c9e3dc59161bd797de70d1d478115bb4c8c
          path: .makoto-core
          persist-credentials: false
      - uses: astral-sh/setup-uv@v6
      - name: Verify the received bundle
        id: verify
        shell: bash
        env:
          HANDOFF: ${{ matrix.handoff }}
          EXPECTED_MANIFEST: ${{ matrix.manifest }}
          EXPECTED_HEAD: ${{ matrix.head }}
        run: |
          verify() {
            uv run --project .makoto-core makoto verify bundle "handoffs/$HANDOFF/bundle" \
              --policy receiver/policy.json \
              --schema-catalog receiver/catalog.json \
              --expected-manifest "$EXPECTED_MANIFEST" \
              --expected-head "$EXPECTED_HEAD" \
              --expected-artifact "receiver/expected/$HANDOFF.artifact.json" \
              --evaluation-time "$EVALUATION_TIME" "$@"
          }
          status=0
          verify --json > makoto-report.json || status=$?
          verify || true
          uv run --project .makoto-core makoto report level makoto-report.json \
            --require "$REQUIRED_LEVEL" || status=1
          exit "$status"
      - name: Keep the verification report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: makoto-report-${{ matrix.handoff }}
          path: makoto-report.json

  merge-check:
    # Runs only when every handoff in the matrix was allowed.
    needs: gate
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Report the render-safety result
        run: echo "replace with your existing step"

    Download makoto-gate.yml. The matrix runs the safe and flagged handoffs through the same step.

The correct failure

  1. Verify authenticity Keep the valid signature result. Do not mislabel the content hazard as tampering.
  2. Verify artifact integrity Keep the valid digest result when the received bytes are unchanged.
  3. Apply the required profile Validate the actual structured artifact or relevant predicate extension under the receiver's digest-pinned schema.
  4. Deny on content policy Report the exact rule that failed so the producer can normalize, reject, or explicitly justify the content.

Why this belongs in the provenance story

The profile and result travel with the evidence boundary, so a later recipient can tell the difference between “bytes changed” and “unchanged bytes were never acceptable.” That distinction matters for incident response and remediation.

Concrete content-policy check

InputA JavaScript source file whose visible text matches a safe file but contains 128 invisible variation selectors.
Integrity resultThe digest and signature pass because the bytes have not changed since signing.
Profile resultThe producer cannot attach the receiver's render-safety profile, and the receiver's only origin rule requires it, so the claim is not authorized.
RemediationThe producer removes the hidden codepoints, re-scans, creates new output bytes, and signs a new origin claim that carries the passing scan.

Inspect the safe and flagged byte sequences side by side

What else this handles

  • Zero-width characters hiding content in configuration files and prompts.
  • Bidirectional control abuse that makes code read differently from how it executes.
  • Tag-character sequences embedding data invisible to standard rendering.
  • Any Unicode family where the rendered view diverges from the byte content.

Key insight. Provenance tells you where an artifact came from. Signatures tell you who vouched for it. Render-safety analysis tells you what is actually present in the bytes, even when a reviewer cannot see it. A receiver needs all three.
