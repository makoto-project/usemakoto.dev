Case 03 · dataset release

Ship the data and the evidence needed to refuse it.

A release process can attach more than a checksum. It can publish signed origin and transformation statements, required profiles, an exact handoff, and the verifier inputs a consumer needs.

Evidence boundary. Every terminal block on this page was captured by running the command shown against the checked-in reference fixtures with the Makoto core at commit 731c5c9, which adds assurance levels (makoto#5, not yet released). Its verifier output is identical to the pinned release 0e41afb. The verification report is byte-for-byte the file published under the end-to-end proof. Nothing below was typed by hand.

The problem

A team releases data every sprint: refreshed training sets, configuration bundles, public extracts. Each release should carry evidence of where the data came from and who vouched for it. When that evidence is a manual step it gets skipped, and when it is only a checksum it proves nothing about who produced the bytes.

The harder case is a release that looks perfect. Here the data is byte-identical to the legitimate release, the signed claim is byte-identical to the legitimate claim, and the signature is cryptographically valid. The only difference is whose key made it. A consumer that checks "is this signature valid?" instead of "is this signer allowed to make this claim?" mirrors it.

  2. How it failed

    The data in the poisoned release hashes to the same digest as the real one, and the head statement has the same digest, 962be717…, as the legitimate public-safe statement. What changed is the key that signed that statement.

  3. Put Makoto in the path

    The consumer mirrors a release internally only after the gate allows it. The gate is the same verifier run as every other case; what makes this case bite is the receiver's trust policy.

    The workflow

    # Consumer-side gate for a published dataset release. The
# release is mirrored internally only after Makoto allows it.
#
# Copy to .github/workflows/makoto-gate.yml in the repository that
# receives handoffs. Layout it expects:
#   handoffs/<name>/bundle/                  what the sender transferred
#   receiver/policy.json                     receiver-owned trust policy
#   receiver/catalog.json, receiver/resources/  pinned private schemas
#   receiver/expected/<name>.artifact.json   expected final artifact
name: Makoto gate before release mirror

on:
  workflow_dispatch:
  push:
    paths:
      - "handoffs/**"

permissions:
  contents: read

env:
  # Pinned so these fixtures replay identically. Delete this line to
  # evaluate against the runner clock.
  EVALUATION_TIME: "2026-09-16T16:00:00Z"
  # Minimum assurance level to accept. L3 (anchored) is the only level
  # that implies an allow decision; a deny still fails at any level.
  REQUIRED_LEVEL: L3

jobs:
  gate:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        include:
          # The sender publishes manifest and head digests out of band.
          # The receiver pins them here, never inside the bundle.
          - handoff: unauthorized-signer
            manifest: sha256:362917a88b0f144d29126e0d05a845c2c58864244b1be0c85cff4d23db76b706
            head: sha256:962be71738a0146642d27c87fba3c7338b0f2bb764b113b16867bb4808b11977
    steps:
      - uses: actions/checkout@v4
      # Pin the verifier to an exact core commit, like any dependency.
      # Run it from a checkout: the CLI resolves its core schemas from
      # the repository tree. This commit adds `makoto report level`
      # (makoto-project/makoto#5); move the pin to the merged release.
      - uses: actions/checkout@v4
        with:
          repository: makoto-project/makoto
          ref: 731c5c9e3dc59161bd797de70d1d478115bb4c8c
          path: .makoto-core
          persist-credentials: false
      - uses: astral-sh/setup-uv@v6
      - name: Verify the received bundle
        id: verify
        shell: bash
        env:
          HANDOFF: ${{ matrix.handoff }}
          EXPECTED_MANIFEST: ${{ matrix.manifest }}
          EXPECTED_HEAD: ${{ matrix.head }}
        run: |
          verify() {
            uv run --project .makoto-core makoto verify bundle "handoffs/$HANDOFF/bundle" \
              --policy receiver/policy.json \
              --schema-catalog receiver/catalog.json \
              --expected-manifest "$EXPECTED_MANIFEST" \
              --expected-head "$EXPECTED_HEAD" \
              --expected-artifact "receiver/expected/$HANDOFF.artifact.json" \
              --evaluation-time "$EVALUATION_TIME" "$@"
          }
          status=0
          verify --json > makoto-report.json || status=$?
          verify || true
          uv run --project .makoto-core makoto report level makoto-report.json \
            --require "$REQUIRED_LEVEL" || status=1
          exit "$status"
      - name: Keep the verification report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: makoto-report-${{ matrix.handoff }}
          path: makoto-report.json

  mirror:
    # Runs only when every handoff in the matrix was allowed.
    needs: gate
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Mirror the verified release
        run: echo "replace with your existing step"

    Download makoto-gate.yml.

    The gate also requires an assurance level. After writing the report it runs makoto report level --require "$REQUIRED_LEVEL"; this workflow requires L3, the only level that implies an allow decision.

A release has two independently reviewed artifacts

Data artifact Evidence handoff
Exact files or signed dataset manifest, media types, sizes, and digests. Signed statement graph, roots, heads, required profiles, and final artifact bindings.
Published through the normal data distribution channel. Published with immutable digests and a receiver-verifiable policy example.
Can be mirrored without changing its identity. Can be verified without access to the producer's CI or warehouse.

CI is a trigger, not the attester

A workflow event can initiate generation after release bytes are final. The signer identity, key custody, source claim, exact predecessor graph, and expected release manifest still require explicit policy. A green CI badge alone is not provenance.

Concrete release receipt

InputThe exact dataset files or deterministic dataset manifest selected for publication.
Release stepCI triggers generation only after bytes are final; a release signer attests the exact graph and handoff.
Consumer stepThe recipient downloads the release and hashes those bytes against the signed final-artifact binding.
Expected failuresA changed file denies on artifact digest (case 01); a correctly signed receipt from an untrusted key denies on authorization (this case).

What else this handles

  • Evidence generated on every release tag instead of remembered by a person.
  • Existing pipelines on any CI system, because the gate is one command and a report file.
  • Batch releases of many files through a signed dataset manifest.
  • Rotating or revoking a release signer by editing receiver policy, without touching published data.

Key insight. Authenticity asks whether a signature is valid for a key. Authorization asks whether the receiver trusts that key for this claim. A release gate that only asks the first question will mirror a perfect forgery.

Release the failure cases too

Consumers need to see the same verifier deny a mutated artifact and unauthorized signer.
