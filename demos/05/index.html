Case 05 · AI dataset gate

Do not train on a label and a checksum.

A shared dataset looks plausible and is validly signed by the producer you trust. Its records carry a field the receiver never allows in training data. Before training, the model builder needs exact bytes, signed source and transformation claims, required content profiles, an authorized handoff, and an independent expectation of what should arrive.

Evidence boundary. Every terminal block on this page was captured by running the command shown against the checked-in reference fixtures with the Makoto core verifier at commit 0e41afb. The pinned core commit 7044f80 adds verification summaries without changing the verifier, and the gate below runs it. Verification-summary tables are computed from the published reports with its property rules. The verification report is byte-for-byte the file published under the end-to-end proof. Nothing below was typed by hand.

The problem

A machine-learning team downloads a training dataset from a shared location. The file name is right, the row count matches, and the columns look correct. Training starts.

What nobody notices is that the privacy step upstream regressed, or was bypassed, and direct identifiers went back into the records. Nothing about the bytes is corrupt, and the producer re-ran its pipeline and signed the new output with its real key. Every integrity check passes, because this is not tampering. It is data the receiver's rules forbid, arriving through a legitimate channel.

The runnable fixture exercises the identifier case: the public-safe step reintroduces an email field and the producer re-signs. A profile that enumerates allowed label values would apply to a re-signed poisoned label the same way; that variant is not among the checked-in fixtures.

  3. Put Makoto in the path

    The training job consumes a verification report, not producer confidence. The gate job must allow the candidate dataset before the train job, which declares needs: gate, is enqueued.

    The workflow

    # Training admission gate. The training job consumes a
# verification report, not producer confidence.
#
# Copy to .github/workflows/makoto-gate.yml in the repository that
# receives handoffs. Layout it expects:
#   handoffs/<name>/bundle/                  what the sender transferred
#   receiver/policy.json                     receiver-owned trust policy
#   receiver/catalog.json, receiver/resources/  pinned private schemas
#   receiver/expected/<name>.artifact.json   expected final artifact
name: Makoto gate before training

on:
  workflow_dispatch:
  push:
    paths:
      - "handoffs/**"

permissions:
  contents: read

env:
  # Pinned so these fixtures replay identically. Delete this line to
  # evaluate against the runner clock.
  EVALUATION_TIME: "2026-09-16T16:00:00Z"

jobs:
  gate:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        include:
          # The sender publishes manifest and head digests out of band.
          # The receiver pins them here, never inside the bundle.
          - handoff: private-schema-violation
            manifest: sha256:2c4f46a0b4e5b0443dadbeaf63e48b9ae315701dee0fe18e911b9f165e876f90
            head: sha256:974d80254c105e52e3eb44bdc6a781dd2ab980f4f8357e1fdea160389e765578
    steps:
      - uses: actions/checkout@v4
      # Pin the verifier to an exact core commit, like any dependency.
      # Run it from a checkout: the CLI resolves its core schemas from
      # the repository tree. This is the core commit the hosted
      # schemas are pinned to.
      - uses: actions/checkout@v4
        with:
          repository: makoto-project/makoto
          ref: 7044f803dc300cd3b7f8b24f40a0bb9d7151113f
          path: .makoto-core
          persist-credentials: false
      - uses: astral-sh/setup-uv@v6
      - name: Verify the received bundle
        id: verify
        shell: bash
        env:
          HANDOFF: ${{ matrix.handoff }}
          EXPECTED_MANIFEST: ${{ matrix.manifest }}
          EXPECTED_HEAD: ${{ matrix.head }}
        run: |
          verify() {
            uv run --project .makoto-core makoto verify bundle "handoffs/$HANDOFF/bundle" \
              --policy receiver/policy.json \
              --schema-catalog receiver/catalog.json \
              --expected-manifest "$EXPECTED_MANIFEST" \
              --expected-head "$EXPECTED_HEAD" \
              --expected-artifact "receiver/expected/$HANDOFF.artifact.json" \
              --evaluation-time "$EVALUATION_TIME" "$@"
          }
          status=0
          verify --json > makoto-report.json || status=$?
          verify || true
          exit "$status"
      - name: Keep the verification report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: makoto-report-${{ matrix.handoff }}
          path: makoto-report.json

  train:
    # Runs only when every handoff in the matrix was allowed.
    needs: gate
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Enqueue the training job
        run: echo "replace with your existing step"

    Download makoto-gate.yml.

    The gate keeps the JSON report as a build artifact, so a later job can summarize it into a signed verification summary without running verification again.

The admission decision

Check Training gate
Origin and transformations Every head traces through exact predecessor bindings to an accepted source claim.
Signer authorization Each key is allowed for the source, operation, profile, or handoff role it signed.
Required profiles Labels, schema, allowed values, identifier rules, and other organization-specific constraints pass.
Handoff completeness and freshness The expected manifest or head matches the signed graph presented for this training run.
Received bytes The actual dataset or dataset manifest matches the signed artifact binding.

A valid gate is not a quality score

The verifier can establish that exact bytes match authorized signed claims and required schemas. It cannot prove the labels are correct, the dataset is unbiased, or the model will be safe. Those require separate evaluation evidence and policy.

Concrete training gate

InputA received dataset bundle, receiver trust policy, local schema catalog, expected head or manifest, and expected artifact binding.
GateRun complete bundle verification before enqueueing the training job.
AllowAll required checks pass and the report decision is allow.
DenyA validly re-signed dataset that reintroduces a direct identifier fails the receiver's private artifact profile with E_PROFILE_INVALID.

What else this handles

  • Training-set versioning across model iterations, with the exact digest of each version.
  • Documented data provenance for regulated AI systems.
  • Datasets assembled from many sources, each verified independently.
  • Retraining pipelines that must reject stale or non-conforming data automatically.

Key insight. A model is only as trustworthy as its training data, and trust needs verification against the receiver's own rules, not the producer's assurance that the pipeline ran.

Fail before the GPU queue

Make the training job consume a verification report, not producer confidence.
