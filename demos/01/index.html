Case 01 · poisoned pipeline

Find every artifact descended from the bad source.

Bytes change after they were signed. The signatures still check out and the metadata still describes the original. The immediate gate matters, and so does the blast radius once the batch has already moved.

Evidence boundary. Every terminal block on this page was captured by running the command shown against the checked-in reference fixtures with the Makoto core at commit 0e41afb. The verification reports are byte-for-byte the files published under the end-to-end proof. Nothing below was typed by hand.

The problem

An ingestion pipeline takes files from partner systems every hour and loads them straight into analytics. Nobody checks where a file came from or whether it changed on the way. The pipeline trusts whatever lands in the drop directory.

One morning a file slips through that is not the file the producer released. Dashboards absorb it, alerts fire on phantom anomalies, and the team spends days finding the source, because there is no record of who produced the file, which exact bytes they vouched for, or what else was built from it.

This case runs that failure against the reference customer-data handoff: a source export, two signed transformations, and a signed handoff to a downstream team. After the handoff is signed, one byte is appended to the final artifact.

  2. How it failed

    The poisoned copy differs from the signed file by a single trailing byte. Everything that describes the file is untouched: the signed handoff manifest and all three signed statements are byte-identical to the good bundle. A pipeline that trusts the metadata, or only checks that the signatures are valid, accepts it.

    $ final=artifacts/final/74ca1fffa13e171a10e838cf6a1516167ae8de5420f331974d0bcbdc7f67db76.bin

  3. Put Makoto in the path

    The receiver adds one gate job in front of the load job. It checks out the verifier at a pinned core commit, runs makoto verify bundle against every received handoff, keeps the machine-readable report as a build artifact, and fails the job on any deny. The load job declares needs: gate, so poisoned bytes never reach it.

    The workflow

    # Receiver-side gate for the poisoned-pipeline case. Nothing
# downstream loads until Makoto allows the exact bytes that arrived.
#
# Copy to .github/workflows/makoto-gate.yml in the repository that
# receives handoffs. Layout it expects:
#   handoffs/<name>/bundle/                  what the sender transferred
#   receiver/policy.json                     receiver-owned trust policy
#   receiver/catalog.json, receiver/resources/  pinned private schemas
#   receiver/expected/<name>.artifact.json   expected final artifact
name: Makoto gate before load

on:
  workflow_dispatch:
  push:
    paths:
      - "handoffs/**"

permissions:
  contents: read

env:
  # Pinned so these fixtures replay identically. Delete this line to
  # evaluate against the runner clock.
  EVALUATION_TIME: "2026-09-16T16:00:00Z"

jobs:
  gate:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        include:
          # The sender publishes manifest and head digests out of band.
          # The receiver pins them here, never inside the bundle.
          - handoff: positive
            manifest: sha256:b83a5cd1870b8ce1f2931650611f0a19deed0796c0f262e4632efc17981f695c
            head: sha256:962be71738a0146642d27c87fba3c7338b0f2bb764b113b16867bb4808b11977
          - handoff: mutated-final-data
            manifest: sha256:b83a5cd1870b8ce1f2931650611f0a19deed0796c0f262e4632efc17981f695c
            head: sha256:962be71738a0146642d27c87fba3c7338b0f2bb764b113b16867bb4808b11977
    steps:
      - uses: actions/checkout@v4
      # Pin the verifier to an exact core commit, like any dependency.
      # Run it from a checkout: the CLI resolves its core schemas from
      # the repository tree.
      - uses: actions/checkout@v4
        with:
          repository: makoto-project/makoto
          ref: 0e41afbd0c3f1c389d6643bfe279ab159e4f53ac
          path: .makoto-core
          persist-credentials: false
      - uses: astral-sh/setup-uv@v6
      - name: Verify the received bundle
        id: verify
        shell: bash
        env:
          HANDOFF: ${{ matrix.handoff }}
          EXPECTED_MANIFEST: ${{ matrix.manifest }}
          EXPECTED_HEAD: ${{ matrix.head }}
        run: |
          verify() {
            uv run --project .makoto-core makoto verify bundle "handoffs/$HANDOFF/bundle" \
              --policy receiver/policy.json \
              --schema-catalog receiver/catalog.json \
              --expected-manifest "$EXPECTED_MANIFEST" \
              --expected-head "$EXPECTED_HEAD" \
              --expected-artifact "receiver/expected/$HANDOFF.artifact.json" \
              --evaluation-time "$EVALUATION_TIME" "$@"
          }
          status=0
          verify --json > makoto-report.json || status=$?
          verify || true
          exit "$status"
      - name: Keep the verification report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: makoto-report-${{ matrix.handoff }}
          path: makoto-report.json

  load:
    # Runs only when every handoff in the matrix was allowed.
    needs: gate
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Load the verified customer data
        run: echo "replace with your existing step"

    Download makoto-gate.yml. The matrix carries both the untampered handoff and the poisoned one so the same step shows an allow and a deny.

The evidence path

  1. Origin The collector signs the exact source batch and source claims at acquisition.
  2. Normalization The next statement binds the raw batch and predecessor envelope before producing cleaned bytes.
  3. Aggregation Downstream outputs append their own statements instead of editing the earlier history.
  4. Receiver gate The receiver hashes the bytes that arrived, while predecessor links identify every affected descendant.

What the scenario proves

Useful result A deterministic deny naming the failed check, plus a graph that supports impact analysis.
It does not prove That every hidden copy participates, that the source was truthful, or that a signature alone makes the batch safe.
Why metadata alone fails The manifest and statements in the poisoned bundle are byte-identical to the good ones. Only hashing the received bytes against the signed subject digest exposes the change.

What else this handles

  • Third-party data feeds where you cannot inspect the source infrastructure.
  • Regulated environments that require data lineage documentation.
  • Multi-team pipelines where one team's output is another team's input.
  • Automated exchanges between organizations with different trust levels.

Key insight. Without verified provenance a pipeline has no immune system: it accepts everything, including poison. With it, the receiver's own expectations, not the sender's metadata, decide what loads.
