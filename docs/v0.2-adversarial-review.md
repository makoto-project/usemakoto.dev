This record covers the implementation-era whole-document review performed after the historical

## Locked intent

The review preserved these project decisions:

- Makoto starts at the source and records an append-only graph of immutable signed statements.
- The portable core stays small while public or private organizational JSON Schemas can extend
  metadata and validate supported structured artifacts.
- Signature validity, signer authorization, graph continuity, handoff completeness/freshness,
  and artifact-byte integrity remain distinct results.
- The September proof is a runnable producer-to-consumer handoff with positive and negative
  verification, not a static JSON example.
- Formal governance, foundation affiliation, named third-party integrations, transparency
  infrastructure, and a production streaming protocol remain outside v0.2. Public participation
  through issues, review, tests, examples, and patches is part of the project.

## Accepted Fable findings

The protocol/security review found no release-blocking written defect, but identified four
material clarifications that were accepted into the specification and adopter documentation:

1. Dataset-manifest `declaredSize` retention and size-mismatch behavior are explicit.
2. Expected manifest, head, and artifact values are independent selection or rollback anchors;
   an expected-head-only check is not a general proof of temporal freshness.
3. Historical verification requires retaining the exact trust-policy snapshot, and key rotation
   needs archived-policy or continued-public-key guidance.
4. An outer DSSE envelope and its decoded payload have different identities: transport paths and
   envelope signatures do not replace the payload digest used for graph identity.

## Rejected or phase-gated findings

- Fable's concern that signature-entry bootstrap overflow lacked deterministic ownership was
  rejected because the specification already assigns the condition to `E_RESOURCE_LIMIT`, Step
  4, owned by `core-schemas`.
- Missing Phase 0 coverage vectors, bounded workers, full resource accounting, complete
  partial-evidence/quarantine reporting, hosted proof, and immutable release evidence are not
  treated as defects in the project plan. They remain explicit blockers to a conformance or
  release claim.

## Current conclusion

The valid Fable review supports the accepted security and adopter clarifications. It does not
establish current-revision cross-model agreement. Appendix B therefore correctly keeps Round 30
open: a future exact `claude-fable-5` whole-document review and an exact `gpt-5.6-sol` `xhigh`
whole-document review must both complete against one frozen revision before the project can claim
that no written specification blocker remains.

Even successful reviewer convergence would not establish wire-protocol conformance. That still
requires the schemas, diagnostic coverage matrix, conformance vectors, bounded implementation,
runnable demo, immutable tag, hosted byte parity, CORS/content-type checks, and release evidence
defined by the specification.

## Adopter-framework review, August 24, 2026

This later review covered the focused adopter model and six-scene public walkthrough, not the
2,785-line normative specification. It therefore does not change the whole-document convergence
status above.

| Reviewer | Route | Version | Setting | Availability and result |
|---|---|---:|---|---|
| `claude-fable-5` | Claude CLI | `2.1.243` | high effort | Stream initialization and response both reported the exact model; two complete independent rounds |
| `gpt-5.6-sol` | Codex orchestration | service route | `xhigh` | Spawned with exact model and setting; two complete independent rounds |

An attempted Codex CLI smoke test requested `gpt-5.6-sol` at `xhigh` but the model response
reported `ultra`. It was excluded under the no-fallback/no-setting-substitution rule. No GPT-4o,
retired model, or Gemini result was used.

Round 1 tested the origin → changes → handoff → receiver story and found that the focused packet
omitted several semantics already present in the normative specification. The revised whole packet
then made those semantics explicit: independently provisioned expectations; signed `issuedAt` plus
age, nonce, replay, and rollback distinctions; private-profile resolution versus authorization;
join and fan-out semantics; untrusted bundle indexing; evaluation-time key authorization; complete
safe failure collection plus a deterministic primary error; offline equivocation limits; and the
partitioned dataset path.

Round 2 found no release-blocking framework error and no unresolved product decision. The accepted
adopter improvements are recorded in [`adopter-framework.md`](adopter-framework.md) and the checked
walkthrough artifacts:

- the handoff manifest remains the only normative summary record;
- expected values are shown as receiver-controlled inputs, never derived from the bundle;
- a key ID is explained through receiver policy instead of presented as a human identity;
- freshness remains visible and signer-asserted time is not presented as trusted event time;
- private schema bytes and their closure must be provisioned separately, and digest identity is not
  rule authorization or confidentiality;
- pseudonymization is described as linkable rather than anonymous;
- unsafe bundle bytes are not parsed after a digest failure;
- the walkthrough includes byte mutation, unauthorized signer, and internally consistent schema
  violation stories; and
- re-serialization, partitioned datasets, metadata privacy, stale policy, and reproducibility limits
  are named without expanding the wire model.

Sol recommended a Parquet-aware profile verifier over the existing dataset-manifest capability.
Fable recommended a pinned canonical-NDJSON profile for common re-serialization workflows. Both are
useful future implementation ideas, not blockers to the current framework or walkthrough.

The two approved reviewers converged only on the adopter framework after revision. Their agreement
does not establish protocol correctness, conformance, implementation safety, or release readiness.

A subsequent Sol xHigh implementation audit found two material demo gaps that the prose review had
not exposed. Both were accepted and corrected. The demo now compares the sender candidate against
the checked, receiver-owned `receiver-inputs/accepted-handoff.json` lock before verification,
passes the expected recipient explicitly, and fails when the candidate changes without separate
receiver approval. The full repository gate now regenerates the complete export into an ignored
temporary directory and byte-compares it with the checked artifact tree. This closes the former
possibility that mutually consistent but stale walkthrough and bundle files could pass together.

The audit also confirmed two advisory boundaries. The public walkthrough intentionally displays
one artifact-content JSON Schema even though the full runnable proof also uses a separate predicate
metadata profile. That distinction is explained on the page rather than weakening the proof. A
future Parquet-aware profile and pinned canonical-NDJSON profile remain useful extensions, not
requirements for this walkthrough.

Sol then re-reviewed the corrected implementation at `xhigh` and found no remaining release
blocker or material risk in the adopter walkthrough. The remaining operational caveat is explicit:
the demo's receiver lock shares a source repository with producer code, so code-review ownership
models the administrative separation. Real deployments still require a recipient-administered
expectation channel.
