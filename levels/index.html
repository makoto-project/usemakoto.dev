Assurance levels

Three levels. Each one is a set of checks you can inspect.

Like SLSA, Makoto names progressive levels so a receiver can say “L2 or higher” in one phrase. Unlike a badge, every level is a fixed set of verification-report checks: when a handoff falls short, the report names exactly which check stopped it.

Key principle. Start at L1 and climb as the decision demands it. Each level is useful on its own, and each includes everything below it. A level is always relative to the receiver's own policy, schema catalog, and expectations.

Status. The level definitions and the makoto report level command are proposed in makoto#5 and are not yet in the pinned core release. The verification checks they read are already in that release.

Check the level of any report

makoto report level reads a report written by makoto verify bundle --json, prints each level with the checks that fell short, and exits 1 when a required level is not met. The two runs below are real output against the published allow and tampered-bytes reports.

$ makoto report level makoto-report.positive.json --require L3
PASS        L1 Provenance is authentic
PASS        L2 Provenance is authorized and complete
PASS        L3 Provenance is anchored
LEVEL       L3
REQUIRED    L3 met
$ echo $?
0
$ makoto report level makoto-report.mutated-final-data.json --require L3
PASS        L1 Provenance is authentic
FAIL        L2 Provenance is authorized and complete: artifact-bytes fail
FAIL        L3 Provenance is anchored: decision deny
LEVEL       L1
REQUIRED    L3 not met
$ echo $?
1

With --json, the command writes one deterministic object with decision, level, and a levels array of satisfied and unmetChecks per level, so a gate or dashboard can record exactly why a handoff fell short.

Seven dimensions behind the levels

The levels group seven separate answers. A report keeps all seven, so a receiver can always read past the level to the evidence.

DimensionEvidence requiredWhat it does not establish
Structure (L1)Core schemas and any required organizational profiles pass.Who signed the claim or whether it is complete.
Authenticity (L1)DSSE signatures authenticate the exact payload bytes.Whether that key was permitted to make the claim.
Authorization (L2)Receiver policy authorizes each key for its source, operation, profile, or handoff role.Whether the claimed event really happened.
Continuity (L2)Every transformation binds exact predecessor statements and input artifact digests.Whether an entire branch was withheld.
Completeness (L2)A signed handoff commits to exact roots, heads, statements, profiles, and final artifacts.Whether an older complete handoff was replayed.
Artifact integrity (L2)The receiver hashes the bytes it actually received and matches the signed subject.Whether those unchanged bytes are safe or useful.
Freshness (L3)An independent expected head, manifest, nonce, artifact, or age bound matches.Data quality or source truthfulness.

Climbing the levels

  1. Start at one source (toward L1)Choose a real collection boundary and bind a signed origin claim to exact source bytes.
  2. Append one transform (toward L1)Make the next producer name its exact predecessor statement and input artifact instead of rewriting a shared history.
  3. Separate the receiver (L2)Move trust policy, authorization rules, and schema catalogs outside the producer's bundle.
  4. Sign the handoff (L2)Commit to the exact graph and artifacts intentionally transferred across the organizational boundary, and add private profiles for the rules that matter.
  5. Anchor it (L3)Pin the expected manifest, head, or artifact through an independent channel, or require a nonce or maximum age.

The same climb with the reference CLI

These are the command shapes the reference end-to-end proof runs, with its paths shortened. Steps 1 to 4 use flags that exist in the pinned core release; step 6 needs makoto#5.

# 1. Start at one source: sign an origin claim over exact bytes.
makoto key generate --private-out keys/origin.private.pem --public-out keys/origin.public.pem
makoto attest origin \
  --subject customers.raw.json=data/customers.raw.json \
  --source-kind urn:makoto:demo:source:synthetic-file \
  --source-uri urn:makoto:demo:v0.2:source:customers-raw \
  --event-id urn:uuid:11111111-1111-4111-8111-111111111111 \
  --occurred-at 2026-09-16T16:00:00Z \
  --key keys/origin.private.pem \
  --out attestations/01-origin.dsse.json

# 2. Append one transform that binds its predecessor and input bytes.
makoto attest transform \
  --subject customers.normalized.json=data/customers.normalized.json \
  --input-binding bindings/normalize-input.json \
  --operation-type urn:makoto:demo:operation:normalize \
  --operation-name "Normalize customer records" \
  --event-id urn:uuid:22222222-2222-4222-8222-222222222222 \
  --occurred-at 2026-09-16T16:00:00Z \
  --key keys/normalize.private.pem \
  --out attestations/02-normalize.dsse.json

# 3. Separate the receiver: check its own policy before trusting it.
makoto policy check --policy receiver/policy.json

# 4. Sign the handoff over the exact graph and final artifact.
makoto handoff create \
  --head attestations/03-public-safe.dsse.json \
  --attestations attestations \
  --artifact-binding bindings/final-artifact.json \
  --schema-catalog receiver/catalog.json \
  --key keys/handoff.private.pem \
  --out bundle

# 5. Verify as the receiver, with receiver-held expectations for L3.
makoto verify bundle bundle \
  --policy receiver/policy.json \
  --schema-catalog receiver/catalog.json \
  --expected-manifest sha256:<published manifest digest> \
  --expected-head sha256:<published head digest> \
  --expected-artifact receiver/expected-artifact.json \
  --json > report.json

# 6. Require a level.
makoto report level report.json --require L3

Run the whole path, including private profiles and seven denial cases, with the end-to-end proof. Put steps 5 and 6 in CI with any casebook gate workflow.

What no level claims

No level calls data “unforgeable,” proves that transformation code executed, certifies a source as truthful, establishes legal compliance, or makes unchanged content safe. Hardware-backed keys, isolated builders, transparency logs, access controls, and governance systems may strengthen a deployment; a future level for isolated evidence generation is reserved until its evidence and conformance tests exist.

Earlier Makoto drafts used the same three names with different requirements: provenance exists, provenance is signed, provenance is generated by isolated infrastructure. Those requirements are not these levels, and a claim made under them does not carry over. The current levels are defined only by checks the reference verifier runs.
