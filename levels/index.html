Assurance model

Trust is a set of answers, not a level badge.

A provenance document can exist and still be unsigned. A signature can be valid and still come from the wrong party. A graph can be continuous and still omit a branch. Makoto reports these checks separately so a receiver can write policy around the evidence it actually needs.

Key principle. Start with one honest boundary and add requirements as the decision demands them. Each dimension below is useful on its own, and none of them is a shortcut for another.

Seven dimensions the receiver evaluates

DimensionEvidence requiredWhat it does not establish
StructureCore schemas and any required organizational profiles pass.Who signed the claim or whether it is complete.
AuthenticityDSSE signatures authenticate the exact payload bytes.Whether that key was permitted to make the claim.
AuthorizationReceiver policy authorizes each key for its source, operation, profile, or handoff role.Whether the claimed event really happened.
ContinuityEvery transformation binds exact predecessor statements and input artifact digests.Whether an entire branch was withheld.
CompletenessA signed handoff commits to exact roots, heads, statements, profiles, and final artifacts.Whether an older complete handoff was replayed.
FreshnessAn independent expected head, manifest, nonce, artifact, or age bound matches.Data quality or source truthfulness.
Artifact integrityThe receiver hashes the bytes it actually received and matches the signed subject.Whether those unchanged bytes are safe or useful.

Each dimension in detail

Every verification report records one status per check. The tables below map each dimension to the report checks that establish it, the diagnostics that deny it, the threats it answers, and the casebook demo that exercises it with real fixtures.

Structure

“The evidence is well-formed, bounded, and matches the schemas the receiver requires.”

Report checksload-safely, parse-strictly, core-schemas, metadata-profiles, artifact-profiles
RequirementSafe bundle paths and resource bounds; strict JSON with no duplicate keys; core statement, handoff, and policy schemas; every critical profile resolved from the receiver's local catalog by root and closure digest.
Denies withE_BUNDLE_UNSAFE_PATH, E_RESOURCE_LIMIT, E_JSON_DUPLICATE_KEY, E_CORE_SCHEMA, E_PROFILE_UNRESOLVED, E_PROFILE_INVALID
Threats answeredD7 privacy violation in content, D9 display-layer obfuscation, profile substitution, resource exhaustion
Use it forOrganization-specific rules: forbidden identifiers, allowed label values, required scan results.
Runnable proofCase 05 denies a validly signed dataset on its private profile.

Authenticity

“These exact statement bytes were signed by this key, and nobody edited them since.”

Report checksindex-payloads, signatures
RequirementEvery statement and handoff is a DSSE envelope; the verifier recomputes each statement digest from decoded payload bytes and verifies every signature against a configured public key.
Denies withE_STATEMENT_DIGEST, E_SIGNATURE_INVALID, E_ENVELOPE_MALFORMED, E_PAYLOAD_TYPE
Threats answeredD6 attestation forgery
Use it forAny evidence that crosses a storage or network boundary you do not control.
Runnable proofCase 04 edits a signed record two ways.

Authorization

“The receiver allows this key to make this kind of claim.”

Report checksauthorization-thresholds, authorization
RequirementEach statement satisfies a receiver rule matching its predicate type and, for origins, source kind and URI, or for transformations, operation type, with the rule's minimum signature count and any profile constraints. Key validity windows are evaluated at the receiver's evaluation time.
Denies withE_SIGNER_UNAUTHORIZED
Threats answeredD1 source impersonation, D5 unauthorized attribution
Use it forSeparating duties: the collector signs origins, the privacy job signs public-safe outputs, and neither can sign the other's claims.
Runnable proofCase 03 denies a valid signature from a known but unauthorized key.

Continuity

“Every step names the exact step and bytes it consumed, back to a declared origin.”

Report checksgraph-dependency-artifacts, graph, roots-and-heads
RequirementEach transformation input binds a predecessor statement digest, predecessor subject name, and input artifact digest that equals the predecessor's output; the graph is acyclic and every head reaches an origin.
Denies withE_PREDECESSOR_MISSING, E_PREDECESSOR_SUBJECT, E_INPUT_DIGEST, E_GRAPH_CYCLE, E_ROOT_INVALID
Threats answeredD3 lineage falsification
Use it forReproducibility, impact analysis, and postmortems that need to walk from an output back to its source.
Runnable proofCase 02 removes and rewires a step.

Completeness

“This is the whole graph the sender meant to hand over, not a convenient subset.”

Report checkscompleteness-anchor
RequirementA handoff manifest signed by an authorized handoff key commits to the exact statement, root, head, required-profile, and final-artifact sets, and those sets equal what the bundle presents.
Denies withE_HANDOFF_REQUIRED, E_MANIFEST_SET, E_REQUIRED_PROFILE_MISSING
Threats answeredBranch omission, D3 lineage falsification
Use it forAny transfer across an organizational boundary.
Runnable proofCase 02 fails completeness when a statement is dropped.

Freshness

“This is the handoff I expected now, not an older valid one.”

Report checksfreshness-anchors
RequirementAt least one receiver-held anchor unless replay is explicitly allowed: expected manifest digest, expected head set, expected final-artifact set, a consumer nonce, or a maximum age at a consumer-controlled evaluation time.
Denies withE_EXPECTED_MANIFEST, E_EXPECTED_HEAD, E_EXPECTED_ARTIFACT, E_HANDOFF_NONCE, E_HANDOFF_STALE, E_FRESHNESS_REQUIRED
Threats answeredD4 timestamp manipulation and replay
Use it forGates that must not accept yesterday's valid release as today's.
Runnable proofEvery casebook gate pins the expected manifest and head. No replay denial is checked in yet.

Artifact integrity

“The bytes I received are the bytes that were signed.”

Report checksartifact-bytes
RequirementThe verifier streams SHA-256 over each received final artifact, and over supplied dataset partitions, and compares it with the signed subject or manifest entry digest.
Denies withE_ARTIFACT_DIGEST, E_ARTIFACT_SIZE, E_ARTIFACT_MISSING
Threats answeredD2 data tampering
Use it forEvery load, mirror, or training job.
Runnable proofCase 01 denies a one-byte change after signing.

Adopt one honest boundary at a time

  1. Start at one sourceChoose a real collection boundary and bind the origin claim to exact source bytes.
  2. Append one transformMake the next producer name its exact predecessor statement and input artifact instead of rewriting a shared history.
  3. Separate the receiverMove trust policy, schema catalogs, expected artifacts, and evaluation time outside the producer's bundle.
  4. Sign the handoffCommit to the exact graph and artifacts intentionally transferred across the organizational boundary.
  5. Add private rulesUse digest-pinned JSON Schema profiles for the organization-specific fields and structured-data constraints that matter to the decision.

The same path with the reference CLI

These are the command shapes the reference end-to-end proof runs, with its paths shortened. Every flag shown exists in the pinned core; makoto <command> --help lists the rest.

# 1. Start at one source: sign an origin claim over exact bytes.
makoto key generate --private-out keys/origin.private.pem --public-out keys/origin.public.pem
makoto attest origin \
  --subject customers.raw.json=data/customers.raw.json \
  --source-kind urn:makoto:demo:source:synthetic-file \
  --source-uri urn:makoto:demo:v0.2:source:customers-raw \
  --event-id urn:uuid:11111111-1111-4111-8111-111111111111 \
  --occurred-at 2026-09-16T16:00:00Z \
  --key keys/origin.private.pem \
  --out attestations/01-origin.dsse.json

# 2. Append one transform that binds its predecessor and input bytes.
makoto attest transform \
  --subject customers.normalized.json=data/customers.normalized.json \
  --input-binding bindings/normalize-input.json \
  --operation-type urn:makoto:demo:operation:normalize \
  --operation-name "Normalize customer records" \
  --event-id urn:uuid:22222222-2222-4222-8222-222222222222 \
  --occurred-at 2026-09-16T16:00:00Z \
  --key keys/normalize.private.pem \
  --out attestations/02-normalize.dsse.json

# 3. Separate the receiver: check its own policy before trusting it.
makoto policy check --policy receiver/policy.json

# 4. Sign the handoff over the exact graph and final artifact.
makoto handoff create \
  --head attestations/03-public-safe.dsse.json \
  --attestations attestations \
  --artifact-binding bindings/final-artifact.json \
  --schema-catalog receiver/catalog.json \
  --key keys/handoff.private.pem \
  --out bundle

# 5. Verify as the receiver, with receiver-held expectations.
makoto verify bundle bundle \
  --policy receiver/policy.json \
  --schema-catalog receiver/catalog.json \
  --expected-manifest sha256:<published manifest digest> \
  --expected-head sha256:<published head digest> \
  --expected-artifact receiver/expected-artifact.json

Run the whole path, including private profiles and seven denial cases, with the end-to-end proof. Put step 5 in CI with any casebook gate workflow.

Claims Makoto deliberately does not compress into a badge

Makoto does not call data “unforgeable,” prove that transformation code executed, certify a source as truthful, establish legal compliance, or make unchanged content safe. Hardware-backed keys, isolated builders, transparency logs, access controls, and governance systems may strengthen a deployment, but each remains a separate claim with its own evidence and policy.

Earlier Makoto drafts graded provenance as three levels: provenance exists, provenance is signed, provenance is generated by isolated infrastructure. That scale hid the difference between a valid signature and an authorized one, and between a continuous graph and a complete one. The current model reports each answer separately. Isolated builders and hardware-backed keys are outside the current protocol.
