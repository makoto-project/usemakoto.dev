Apache Airflow with Makoto

DAG-driven orchestration — record signed evidence at the task boundaries that actually create durable data.

Design note: This is an implementation pattern, not a shipped adapter. The attachment points use real Apache Airflow APIs; the Makoto calls show where signed evidence would enter the lifecycle.

What is Apache Airflow?

Apache Airflow schedules tasks and records their execution context. A DAG edge alone does not identify exact data bytes, but a sensor, materializing task, or publish callback can capture the artifact, predecessor statement, operation identity, and signer needed for portable evidence.

Sensor successObserve a stable source object and attest its exact digest
Task outputBind a materialized artifact to predecessor evidence and an operation
DAG completionAssemble a signed handoff only after required heads exist
Receiver gateVerify outside Airflow with independent policy and expected bytes

Where Makoto attaches

Primary pattern: Operator + on_success_callback. Below are the integration options ordered by lift required.

How Makoto attaches to Apache Airflow

  • Sensor callback — After a sensor resolves a stable object or partition, hash the bytes and create an origin statement. The sensor event is context; the artifact digest is identity.
  • Materialization callback — After a task commits output, create a transformation statement that binds the output to the exact upstream statement and subject.
  • OpenLineage input — Existing events can supply job and dataset context, but an adapter must still resolve exact artifact bytes, Makoto predecessor digests, and an authorized signing boundary.
  • DAG-level handoff — A final task can collect the signed heads and artifacts into a handoff for another team; it must not infer completeness from task success alone.

Implementation sketch

Call the reference CLI after materialization

This shell task uses real Makoto commands. The operator must supply stable paths, an input binding, and a protected signing key.

# A BashOperator or callback runs only after orders.parquet is committed.
# input-binding.json names the input bytes, predecessor envelope,
# and predecessor subject. Airflow does not invent those values.
uv run makoto attest transform \
  --subject "orders.parquet=/data/orders.parquet" \
  --input-binding /evidence/input-binding.json \
  --operation-type "urn:example:airflow:task" \
  --operation-name "sales_etl.hash_pii" \
  --operation-metadata /evidence/airflow-task.json \
  --key "/run/keys/transform.private.pem" \
  --out /evidence/transform.dsse.json

# A later handoff task can collect signed heads and artifacts.
uv run makoto handoff create --help

Where this pattern would matter

Daily ETL

Each materializing task can leave a signed, hash-linked record of the exact inputs and outputs it claims.

Compliance Audit

Auditors can compare signed evidence with Airflow history without relying on scheduler logs as the trust anchor.

Multi-team Handoff

Downstream teams can refuse parquet files whose signed handoff, graph, signer policy, or received-byte digest fails.

Data Contract Enforcement

Schema and hash mismatches surface as task failures, not silent corruption.
