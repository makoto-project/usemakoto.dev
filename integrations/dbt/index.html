Integration field note

dbt with Makoto

Turn committed model outputs and dbt run metadata into signed transformation evidence.

Design note: This is an implementation pattern, not a shipped adapter. The attachment points use real dbt APIs; the Makoto calls show where signed evidence would enter the lifecycle.

What is dbt?

dbt materializes SQL models and records declared lineage, code, tests, and run results. Those files are useful operation metadata, but Makoto still needs stable input and output artifacts plus predecessor statements before it can make a portable transformation claim.

Manifest contextmanifest.json identifies models, dependencies, and compiled code
Run completionrun_results.json identifies the materializations that actually finished
Model VersioningModel versions map cleanly to attestation subjects
Test resultsOrganizational profiles can require explicit test evidence without calling it source truth

Where Makoto attaches

Primary pattern: post-hook macro + on-run-end. Below are the integration options ordered by lift required.

How Makoto attaches to dbt

  • Run-results exporter — After a successful materialization, resolve the output to stable exported bytes, then call the reference CLI with the dbt artifacts as operation metadata.
  • Model post-hook — A hook can enqueue evidence generation, but it should not sign a table before the transaction commits or claim a relation digest it never computed.
  • Source observation — Source freshness is context, not proof of exact source bytes. Create an origin only where a stable snapshot or export can be hashed.
  • Cloud run webhook — A webhook can trigger the same exporter; signing keys, predecessor resolution, and handoff policy remain operator-owned.

Implementation sketch

Export, bind, then attest

The exporter runs after dbt reports success and after the warehouse output has been serialized to stable bytes.

# dbt invokes an operator-owned exporter on run completion.
dbt run --select marts.sales.dim_customers

# Export the committed model deterministically before hashing it.
warehouse-export marts.sales.dim_customers > /artifacts/dim_customers.parquet

# dbt-run.json may include invocation_id, unique_id, compiled SQL digest,
# adapter identity, and test results. input-binding.json resolves the
# exact predecessor statement and input artifact.
uv run makoto attest transform \
  --subject "dim_customers.parquet=/artifacts/dim_customers.parquet" \
  --input-binding /evidence/input-binding.json \
  --operation-type "urn:example:dbt:model" \
  --operation-name "model.marts.dim_customers" \
  --operation-metadata /evidence/dbt-run.json \
  --key /run/keys/transform.private.pem \
  --out /evidence/dim_customers.dsse.json

Where this pattern would matter

Marketplace Models

Sell or share dbt models with cryptographic proof of which sources fed them.

Regulated Reporting

SOX, HIPAA, GDPR — every reporting model carries a signed lineage record.

Cross-warehouse Audit

Snowflake → BigQuery migration? Makoto evidence prove the destination model matches the source.

Failed Test Visibility

Models that ship with failing tests are flagged in the Makoto evidence, not silently used.
