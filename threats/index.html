Threat model

Signed history can still be false, incomplete, stale, or unsafe.

Makoto makes exact claims attributable and tamper-evident. It does not turn every signed claim into truth. The receiver must evaluate distinct failure modes instead of treating “signature valid” as a universal pass.

The data supply-chain threat catalogue

Data pipelines face threats that software build pipelines do not: readings that were never taken, rows that changed after sign-off, lineage that skips the step that mattered, and content that passes every integrity check because it was bad when it was signed. The catalogue below names nine of them. Each entry lists the attack, the verifier check and diagnostic codes that answer it, the track level or verified property that addresses it (following the core failure-mode coverage matrix), what remains outside Makoto, and the casebook demo that runs it against real fixtures when one exists.

D1 · Source impersonation

An attacker claims data originates from a trusted source when it does not: fake sensor readings, forged API responses, spoofed device identifiers.

Verifier controlOrigin statements are signed over exact source bytes. Receiver policy authorizes origin claims per key and per sourceKinds (and optionally exact sourceUris), so a key trusted for one source cannot vouch for another.
DiagnosticsE_SIGNATURE_INVALID, E_SIGNER_UNAUTHORIZED, E_ARTIFACT_DIGEST
Residual riskAn authorized collector or platform can still lie. Makoto cannot establish physical truth, that a signer told the truth, or that the source was correct.
Level / propertyOrigin L1 supplies the attributable claim; Origin L2 authenticates the capture platform; MAKOTO_AUTHORIZED evaluates receiver authority, which requires an origin rule for the key and source.
Runnable proofCase 06 denies an origin claim that no origin rule authorizes.

D2 · Data tampering

Unauthorized modification of data in transit or at rest: a man-in-the-middle rewrite, storage compromise, or an injected row after sign-off.

Verifier controlThe receiver hashes the exact bytes it received and compares them with the signed subject digest. Partitioned datasets commit each entry digest and optional size through a dataset manifest.
DiagnosticsE_ARTIFACT_DIGEST, E_ARTIFACT_SIZE, E_ARTIFACT_MISSING, E_INPUT_DIGEST
Residual riskA producer can sign bytes that were already bad. A historical artifact that is no longer available is reported not_checked, not verified.
Level / propertyOrigin L1 or Transform L1 plus base verification: artifact-bytes must pass. MAKOTO_GRAPH_COMPLETE supports descendant impact analysis.
Runnable proofCase 01 appends one byte after signing and denies with E_ARTIFACT_DIGEST.

D3 · Lineage falsification

False records of transformation history: a missing step, a transformation re-pointed at a different predecessor, a fabricated chain, or a cycle.

Verifier controlEvery transformation input binds the predecessor statement digest, predecessor subject name, and input artifact digest. The graph must reach declared origins without cycles, and the signed handoff commits to the exact statement, root, and head sets.
DiagnosticsE_PREDECESSOR_MISSING, E_PREDECESSOR_SUBJECT, E_INPUT_DIGEST, E_GRAPH_CYCLE, E_ROOT_INVALID, E_MANIFEST_SET; an edited binding without a new signature fails E_SIGNATURE_INVALID
Residual riskA compromised authorized producer can sign a different, internally consistent graph. Transform L2 and L3 reduce but cannot eliminate that risk. Without a trusted Transform-track assessment, Makoto does not prove a described transformation executed.
Level / propertyTransform L1; MAKOTO_GRAPH_COMPLETE. graph, roots-and-heads, and completeness-anchor must pass; an edit that breaks a signature already fails signatures.
Runnable proofCase 02 removes the origin statement and rewires the final step.

D4 · Timestamp manipulation and replay

Temporal metadata is altered to misrepresent when data was collected or handed off: backdated readings, reordered events, or an older valid handoff replayed as current.

Verifier controloccurredAt and issuedAt are signer-asserted claims, not trusted time. Freshness comes from receiver-held anchors: an expected manifest, head set, or final-artifact set; a consumer nonce; or a maxAgeSeconds bound at a consumer-controlled evaluation time. Key validFrom and validUntil are evaluated against that evaluation time, never the signed event time, so backdating cannot restore authorization.
DiagnosticsE_EXPECTED_MANIFEST, E_EXPECTED_HEAD, E_EXPECTED_ARTIFACT, E_HANDOFF_NONCE, E_HANDOFF_STALE, E_FRESHNESS_REQUIRED
Residual riskNo timestamp is proven to come from a trusted clock. Transparency logs are out of scope, so rollback resistance is only as strong as the channel that delivered the expected values.
Level / propertyBase verification; MAKOTO_FRESHNESS_ANCHORED. freshness-anchors must pass with at least one anchor method passing. The same anchors reject 800-day-old records and enforce a three-hour expiry SLO.
Runnable proofNo replay denial is checked in yet. Every casebook gate pins the expected manifest and head, which is the anchor this threat requires.

D5 · Unauthorized attribution

Processing is attributed to a legitimate identity that did not perform it, or a known key signs outside its role: a stolen signing key, a compromised service account, a test key in production.

Verifier controlAuthenticity and authorization are separate checks. A statement must satisfy a receiver rule that lists its key for that predicate type, source, or operation, with a minimum signature threshold. Handoff signers are authorized separately.
DiagnosticsE_SIGNER_UNAUTHORIZED
Residual riskA stolen key that the policy still authorizes passes. Revocation and identity lifecycle remain external: revocation is a local policy edit, and public revocation infrastructure is out of scope.
Level / propertyOrigin L2 or Transform L2 identifies the platform; MAKOTO_AUTHORIZED decides authority: authorization-thresholds and authorization must pass.
Runnable proofCase 03 denies a byte-identical claim signed by a known but unauthorized key.

D6 · Attestation forgery

Attestation documents are edited or substituted so they appear valid: a rewritten operation record with its old signature, an envelope swapped under an unchanged index entry, or a payload crafted to confuse a parser.

Verifier controlDSSE signatures cover the exact payload bytes. The verifier recomputes every statement digest from decoded payload bytes before trusting the bundle index, and parses JSON strictly.
DiagnosticsE_SIGNATURE_INVALID, E_STATEMENT_DIGEST, E_ENVELOPE_MALFORMED, E_PAYLOAD_TYPE, E_JSON_DUPLICATE_KEY, E_JSON_INVALID
Residual riskKey custody is a deployment responsibility. A signer with the key can produce a new, valid forgery, which is why authorization and anchors still matter.
Level / propertyOrigin L2 or Transform L2; base verification: signatures and index-payloads must pass.
Runnable proofCase 04 edits a signed record two ways and denies both.

D7 · Privacy violation

Sensitive information leaks through attestations, reports, or the data itself: source locators that reveal internal systems, extension fields with personal data, correlation across handoffs, or direct identifiers reintroduced into a public dataset.

Verifier controlSource locators are optional and extension payloads are organization-controlled. Private profiles are exchanged separately and resolved from the receiver's local catalog with no network retrieval. A required artifact profile can reject identifiers in structured data.
DiagnosticsE_PROFILE_INVALID, E_REQUIRED_PROFILE_MISSING, E_ARTIFACT_FORMAT for content; metadata minimization has no diagnostic and is a producer obligation
Residual riskProvenance is not encryption and does not make data confidential. Metadata minimization, retention, legal basis, and report handling remain producer and consumer duties; reports can contain recipient and nonce values and must be handled as sensitive evidence.
Level / propertyOrigin L3 may enforce collection minimization; MAKOTO_SCHEMA_CONFORMANT requires the digest-pinned artifact profile, so required artifact-profiles must pass.
Runnable proofCase 05 denies a validly signed dataset that reintroduced email addresses. See privacy techniques.

D8 · Stream injection

Malicious events are inserted into high-throughput streams: spoofed events, manipulated sequences, polluted windows.

Verifier controlThe reference implementation covers finite artifacts. A dataset manifest commits to an exact, sorted set of partition digests, and finite newline-delimited JSON can be validated against a profile under strict line and size bounds.
DiagnosticsE_DATASET_MANIFEST_INVALID, E_DATASET_MANIFEST_REQUIRED, E_ARTIFACT_DIGEST, E_ARTIFACT_SIZE, E_RESOURCE_LIMIT
Residual riskA production streaming or windowing protocol is not part of the current release. A dataset manifest proves the producer's committed partition set, not that a storage prefix contains no other objects.
Level / propertyNo live-stream level exists. Transform L1 applies only after a finite partition is committed; base verification checks committed partitions, and artifact-bytes covers supplied partition bytes.
Runnable proofNone yet. This is an open area for community fixtures.

D9 · Display-layer obfuscation

Content is materially present in artifact bytes but absent, misleading, or hard to notice in common rendered views: invisible variation selectors encoding hidden instructions, zero-width characters, bidirectional control abuse. This is not tampering or lineage falsification. It is a divergence between what humans review and what machines ingest.

Verifier controlA render-safety scan travels as an extension of the signed claim, and a digest-pinned receiver profile requires a passing verdict. The reference producer refuses to attach a profile the claim does not satisfy, and a receiver rule with a profile constraint authorizes nothing without it.
DiagnosticsE_SIGNER_UNAUTHORIZED when no rule's profile constraint is met; E_PROFILE_INVALID when a present profile fails; E_REQUIRED_PROFILE_MISSING when a required profile is absent
Residual riskThe guarantee is only as good as the scanner and the profile. Content validation is normative for JSON artifacts; other formats need adapters.
Level / propertyOrigin L3 can enforce a render-safety control; MAKOTO_SCHEMA_CONFORMANT and MAKOTO_AUTHORIZED. A rule with a render-safety profile constraint must authorize the claim.
Runnable proofCase 06 denies a source file carrying 128 hidden variation selectors. See the invisible Unicode example.

The correctness boundary. Makoto will never certify data-content correctness. A downstream process can consume Makoto's exact origin, operation, signer, graph, profile, and artifact identities, run its own tests, review, or evaluation, and bind that result to the same digests in a separate attestation. See handing off to a correctness process.

Attack surface by pipeline stage

Every stage of a data pipeline is an attack surface. Makoto does not harden the stage; it gives the receiver a verification point that exposes what happened there.

On narrow screens, scroll right to see where each threat is caught.
StageThreatsWhere the receiver catches it
SourceD1 impersonation, D9 hidden contentOrigin rule authorization and required origin profiles.
TransportD2 tampering, D4 replayArtifact digests over received bytes; expected manifest, head, nonce, or age bound.
ProcessingD3 lineage falsification, D5 unauthorized attributionPredecessor and input bindings; per-operation signer rules.
Storage and archiveD6 forgery, D2 tampering at restSignature and statement-digest recomputation on every re-verification.
ConsumerD7 privacy, D8 injected partitionsRequired artifact profiles and dataset-manifest entry checks.

Trust boundaries stay outside the bundle

  1. Signing keysPrivate keys and production signing policy are deployment responsibilities. Demo keys are intentionally insecure fixtures.
  2. AuthorizationThe receiver supplies policy; the producer does not get to declare itself trusted.
  3. Expected stateFreshness requires an expected head, manifest, nonce, artifact, age, or transparency record learned independently.
  4. Schema catalogPrivate profiles remain private and are resolved from authenticated local bytes, never ambient network lookup during verification.

Software supply chain versus data supply chain

SLSA addresses software build integrity. Makoto addresses the threats specific to data moving between producers and receivers. They share principles and differ in focus.

SLSA threats (software)

  • Compromised source repository
  • Modified source after checkout
  • Compromised build platform
  • Uploaded modified package
  • Compromised package registry
  • Dependency confusion
  • Compromised build dependencies

Makoto threats (data)

  • D1 Source impersonation
  • D2 Data tampering in transit or at rest
  • D3 Lineage falsification
  • D4 Timestamp manipulation and replay
  • D5 Unauthorized attribution
  • D6 Attestation forgery
  • D7 Privacy violation
  • D8 Stream injection
  • D9 Display-layer obfuscation

Shared principles and real differences

  • Attestation-based. Both express provenance as verifiable claims about exact artifacts.
  • Same envelope. Makoto statements are in-toto Statements carried in DSSE envelopes.
  • Tamper-evident. Exact-byte SHA-256 digests make modification detectable.
  • Receiver-owned policy. Makoto's receiver decides which keys may make which claims; the bundle never declares itself trusted.
  • Tracks and verified properties. Both separate producer tracks with cumulative levels from receiver results carried in a Verification Summary Attestation. Makoto has Origin and Transform tracks, and a denied handoff still shows exactly which check stopped it. See the comparisons.

Defense in depth

  1. Detection (Origin and Transform L1)Exact-byte digests expose any change to statement payloads and to received artifacts.
  2. Authentication (L2 platforms)DSSE signatures bind each statement and handoff to a key; at L2 that key belongs to a hosted platform, not a person.
  3. Authorization (MAKOTO_AUTHORIZED)Receiver policy limits each key to the sources, operations, profiles, and handoffs it may sign.
  4. Completeness and freshness (MAKOTO_GRAPH_COMPLETE, MAKOTO_FRESHNESS_ANCHORED)A signed handoff defeats omission; an independent anchor defeats replay.
  5. Content policy (MAKOTO_SCHEMA_CONFORMANT, Origin L3)Digest-pinned private profiles reject unchanged bytes that were never acceptable, and Origin L3 enforces them at capture.
  6. PrivacyMinimized metadata and separately exchanged profiles limit what evidence discloses.
Turn attacks into fixtures

A threat becomes useful when it has one exact mutation and one expected denial.

The reference demo already covers artifact mutation, signature failure, predecessor removal, rewiring, private-profile violation, and unauthorized signers, and the casebook runs each through a real gate. Replay and stream injection still need fixtures. Add the case it missed.
