Worked walkthrough · one dataset, start to finish

Attest it. Change it. Attest it again.

A dataset is attested, then edited, then transformed again. Each change produces different bytes, so each change needs its own statement, and each new statement carries the identity of the one before it. This page follows a single set of customer records through all three states and shows the evidence each state produced.

Every value on this page is real. The records are the fixtures checked into the runnable proof, and every digest was computed from those exact bytes. Nothing here is illustrative filler. This page presents evidence; it does not perform verification.

If your pipeline overwrites in place

This page writes a new file at every step. When a job rewrites one table instead, storage only ever holds the latest bytes, yet every state still needs its own statement. The in-place walkthrough runs real SQL against one SQLite table, twice, and attests each state it passes through: same table, new state each step.

  1. The dataset as it arrives

    Three customer records, straight off a partner API. They have the defects real intake data has: padded whitespace, inconsistent case, and a consent field holding three different spellings of the same two answers.

    [{"age":34,"customer_id":"C-1001","email":" Alice@Example.COM ","marketing_consent":" YES ","region":"us"},{"age":67,"customer_id":"C-1002","email":"BOB@EXAMPLE.COM","marketing_consent":"false","region":"gb"},{"age":17,"customer_id":"C-1003","email":" carol@example.com","marketing_consent":"1","region":"ca"}]

    These exact bytes hash to one value, and that value is the only thing an attestation can usefully commit to. A file path can be reused; a name can be reassigned. The digest cannot.

    customers.raw.json
    Size
    311 bytes

  2. Attest it for the first time

    The first statement is an origin. It is the only kind of statement with no predecessor, so it is where a lineage graph is allowed to begin. It answers one question: where did these specific bytes come from?

    Read it from the top. subject names the artifact and pins its digest, so the statement is bound to content rather than to a filename. source records what the bytes were pulled from and when. The operational and governance detail that the earlier format carried as first-class fields — collector identity, origin geography, lawful basis — lives under extensions, which the specification leaves open for exactly this.

    This statement now has an identity of its own, and it is a hash too: the SHA-256 of its canonical serialization. That number is how every later statement will refer back to it.

    Subject digest
    4e90181e7f75ccdf0e4d81c83d281f53806bed241787cdc751e22b2d4cd19919
    Statement digest
    014b4252977a17c8f2423210fc4c123a464efcc36eefa70e4203c3adee1a3b11
    Document
    origin-example.json

    The statement digest is taken over the canonical form of the statement — keys sorted, no insignificant whitespace — not over the pretty-printed file above. That is what makes the identity stable: reformatting a statement, or reordering its keys, cannot change what it is. Reproduce it yourself below.

  3. The dataset changes

    A new file with a new digest: customers.normalized.json. The original customers.raw.json is untouched.

    Now the records get normalized. Whitespace goes, email case is folded, consent becomes a real boolean, region codes are upper-cased.

    [{"age":34,"customer_id":"C-1001","email":"alice@example.com","marketing_consent":true,"region":"US"},{"age":67,"customer_id":"C-1002","email":"bob@example.com","marketing_consent":false,"region":"GB"},{"age":17,"customer_id":"C-1003","email":"carol@example.com","marketing_consent":true,"region":"CA"}]

    FieldBeforeAfterWhat happened
    email" Alice@Example.COM ""alice@example.com"Surrounding spaces stripped, case folded.
    marketing_consent" YES "trueString token resolved to a boolean.

    customer_id"C-1001""C-1001"Carried through unchanged.

    Different bytes, different digest. This is the moment the record would go stale in a system that tracked datasets by name.

    Digest before
    4e90181e7f75ccdf0e4d81c83d281f53806bed241787cdc751e22b2d4cd19919
    Digest after
    421e19cf002aa25cf6f2f9ed788e04c9badfd9cbc6b00030b0b089810b2ae4f8

    The origin statement is not invalidated by this. It was never a claim about a file path or about the current contents of a table; it was a claim about one specific sequence of bytes, and that claim stays true forever. What the change creates is not a contradiction but a gap: there is now a dataset in play that no statement covers.

    Look at the bottom of the document. The inputs block is the new information, and it is what makes this a link rather than an isolated assertion. It carries two digests, and they do different jobs:

    Input digest
    4e90181e7f75ccdf0e4d81c83d281f53806bed241787cdc751e22b2d4cd19919
    inputs[0].digest: the bytes this step consumed. A receiver checks this against the predecessor's subject digest; if they differ, something was swapped between the steps.
    Predecessor
    014b4252977a17c8f2423210fc4c123a464efcc36eefa70e4203c3adee1a3b11
    inputs[0].provenance.statementDigest: the identity of the origin statement from step 02. This is the edge in the graph.

    Because that second value is the hash of the whole previous statement, the edge cannot be rewired quietly. Editing the origin statement in any way — changing a timestamp, adding a field, even reordering it in a way that survives canonicalization — changes its digest, and this pointer stops resolving. Anyone re-signing the origin to cover their tracks has to re-sign every statement downstream of it.

    Note also operation.parametersDigest. The configuration that drove the run is not copied into the statement; it is hashed, so the parameters can be published, withheld, or kept internal without changing what the statement commits to.

  5. Transform it again

    Another new file: customers.public.json. The normalized and raw files stay as they were.

    The normalized data still carries direct identifiers, so it cannot leave. A second transformation produces a public-safe derivative: email dropped, customer id replaced by a pseudonym, exact age generalised into a band.

    [{"age_band":"0-17","customer_id":"2da7dbbb0e3f243b06cb","marketing_consent":true,"region":"CA"},{"age_band":"25-34","customer_id":"3fb57f8f4d704855a7aa","marketing_consent":true,"region":"US"},{"age_band":"65+","customer_id":"ce76ddf0a0df7f1d0add","marketing_consent":false,"region":"GB"}]

  7. What a receiver now sees

    A receiver gets the three statements and one file of bytes. It does not get, and does not need, access to the producer's systems. From the head of the chain it walks backwards to the root, and at every hop it has something checkable.

    The checks it can run on that, alone, at its own desk:

    • Hash the file that actually arrived and compare it to the head statement's subject digestBYTES
    • Hash each statement's canonical form and compare it to the digest its successor claimsGRAPH
    • Confirm every step but the root declares a predecessor, and that the graph terminates at an originCONTINUITY

    Three things this page deliberately does not establish. The statements here are unsigned, so there is no authenticity claim: anyone could have written them. Without signatures there is nothing to authorize, so there is no authorization claim either — and authorization is a receiver policy decision even when signatures are present, not a property of the document. And a chain that is internally consistent can still be an old one replayed, so freshness needs a separate anchor.

    The runnable proof adds all three: Ed25519 signatures over each statement, a receiver-held trust policy that decides which key may sign which kind of step, and an expected manifest, head, and artifact that pin the handoff to this delivery rather than an earlier one. It also carries seven executable tampering cases, each of which breaks exactly one of the checks above.

    For transport, the three statements and the final bytes go into a bundle index, which maps statement digests to paths without adding any authority of its own: dbom-example.json. The set of files themselves can be listed with digests and sizes in a dataset manifest: dataset-manifest-example.json.

Reproduce every digest on this page

No tooling required beyond a shell and Python. Artifact digests are plain file hashes:

curl -sO https://usemakoto.dev/demos/v0.2-end-to-end/artifacts/data/customers.raw.json
shasum -a 256 customers.raw.json

Statement digests are taken over the canonical serialization, so hash that rather than the file:

python3 - <<'EOF'
import hashlib, json, urllib.request

BASE = "https://usemakoto.dev/attestations/"
for name in ("origin-example", "transform-example", "public-transform-example"):
    raw = urllib.request.urlopen(BASE + name + ".json").read()
    canonical = json.dumps(json.loads(raw), sort_keys=True, separators=(",", ":"))
    print(hashlib.sha256(canonical.encode()).hexdigest(), name)
EOF

That prints the three statement digests quoted above, in order. If any of them differs, this page and the documents it serves have drifted apart, and the documents are the ones to believe.

This walkthrough stops short of signing. The runnable proof does not.
