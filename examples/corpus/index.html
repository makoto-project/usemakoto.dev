Guide · a sharded corpus kept in Git

Map a corpus index onto Makoto documents.

Many corpora live as a Git repository of small index files that point at large shards stored elsewhere. This guide follows one such corpus from its directory indexes down to a single shard, and shows which Makoto document carries each part, what a reader can then check, and what stays outside Makoto.

1. Map the index2. Carry licenses3. Maintain it in Git

Every value in this guide is real. scripts/corpus_example.py builds the corpus, signs its record with the Makoto reference CLI at the pinned core commit, runs each command shown, and saves what it printed. The keys are insecure example-only keys derived from fixed seeds. The archive, the letters and the society that transcribed some of them are fictional.

The corpus as it sits in Git

The repository holds index files, manifests and lineage records. The shards, which in a real corpus run to hundreds of megabytes each, live in a separate content-addressed store (a lookaside) and are fetched by digest. They never enter Git.

index.yaml                       lists the directories below it
text/
  index.yaml                     lists letters/
  letters/
    letters.yaml                 leaf manifest: languages, license, sources, shards
    ingest.yaml                  the settings the ingest ran with
    makoto/                      the lineage record for this leaf
lineage/
  policy.json                    which keys may sign which kind of step
  catalog.json                   schemas the policy names
  license.profile.json           the digest-pinned reference to one of them
  schemas/license-v1.schema.json
  check_lineage.py               the pull-request check
.github/workflows/lineage.yml    runs the check and a sign-off check

Every indexable directory has an index.yaml naming the directories below it, so a tool pointed at any directory can walk down to every leaf manifest beneath it.

# Directories beneath this one that hold corpora.
children:
  - text/
children:
  - letters/

The leaf manifest is the file contributors and readers care about. It declares the corpus's languages, its set-level license and evidence for it, the upstream source, and every shard by name, digest and size. Shard letters-00001 carries its own license, which overrides the set's.

Which Makoto document carries which part

Corpus partCarried byStatus
Directory index filesNothing. Makoto has no catalog or directory concept, and forbids hashing a directory by walking it (section 12.5). The tree stays in Git.Stays outside Makoto
Upstream sourceAn origin statement: source.kind, uri, name, version, retrievedAt (section 11.3).Today
Raw files fetched from itEntries in a dataset manifest (name, digest, size, media type) that the origin names as its subject.Today
The ingest runA transform statement. Its input is the raw manifest; operation.tool names the ingester; operation.parametersDigest pins the exact bytes of ingest.yaml (section 11.4).Today
ShardsEntries in a second dataset manifest, a subject of the ingest statement.Today
Leaf manifestThe ingest statement's other subject, handed off as the record's final artifact.Today
The record in GitA handoff bundle in makoto/ beside the manifest, signed by an index maintainer's key (section 13.3).Today
Set and shard licensesA claim in the ingest statement's extensions, required by a profile. Carry licenses shows it.Proposed extension
Languages, record countsWould follow the same pattern as licenses: a named extension and a profile. Not included here.Would need an extension
Row source, license, maintainerColumns in the shard rows. The shard's digest commits to them; no verifier reads them.Stays outside Makoto

The documents, in the order they were signed

Each statement below is the exact payload its signature covers. Copy a block and hash it with shasum -a 256 to get the statement digest quoted beneath it. The signed envelopes are in makoto/attestations/.

The raw files, as a dataset manifest

A directory is not a finite byte sequence, so the ingest lists the files it fetched in a dataset manifest (section 12.5) and the origin names that manifest as its subject.

The shards, as a second dataset manifest

Handoff: the record a reader receives

An index maintainer's key signs the handoff. It fixes the exact set of statements, their root and head, and the artifact handed off: the leaf manifest. The two dataset manifests travel in the bundle as supporting material, because their profile requires their bytes.

Verify the record

A reader runs the verifier from the repository root, with the repository's policy, and names the leaf-manifest bytes they expect. Here the expectation is the file they checked out:

What ALLOW establishes: each statement is signed by a key the policy authorizes for that kind of step; the ingest's license claim validates against the profile the policy demands; the graph runs unbroken from the handoff back to the origin; and the leaf manifest's bytes are the ones the record names.

What it does not: that the archive's rights statement is correct, that the letters were transcribed faithfully, or that any shard you have not supplied is intact.

Limits worth knowing

Parallel work
Makoto records the results of sharded, parallel work. It does not schedule or describe the fan-out. One statement per worker means many statements and keys; one statement per ingest, as here, means trusting whoever aggregated the workers' output.
Scale
The specification's performance target is a 1,000-statement graph verified in at most 2 seconds at p95 (section 23.2). That is a target, not a measurement at the size of a large corpus.
Rows
The finest unit is the shard. Proving that a row belongs to a verified shard would need a new predicate, and current verifiers reject predicates they do not know (section 11.1).
Keys
Signatures use Ed25519 keys named in the reader's policy. Keyless signing, transparency logs and certificate authorities are outside the current specification (section 5).
Replacement
A re-ingest that replaces a corpus produces a new origin and a new head. The reader's policy decides whether an older record is still acceptable.
Implementation
The reference implementation is Python. From Go, drive the pinned CLI through os/exec and read its JSON report, as the Go page shows.
