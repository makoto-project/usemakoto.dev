Worked walkthrough · one table, edited in place

Same table. New state. New statement.

Most tables are not copied at every step; they are updated where they sit. This page runs real SQL against one SQLite table, twice, and attests every state the table passes through. The database keeps only the latest rows. Makoto keeps every state as its own digest, each statement naming the one before it.

Every value on this page is generated. The commands are committed files, scripts/in_place_example.py runs them against a fresh SQLite database, and every export, digest and statement below comes from that run and validates against the published schemas. If your pipeline writes a new file at every step instead, the lifecycle walkthrough follows that shape.

  1. The table and what gets hashed

    One table, created once. The consent column has no declared type, so SQLite stores whatever each command writes into it: text on the way in, integers once normalized.

    -- marketing_consent is declared without a type, so SQLite stores each value
-- exactly as written: text when loaded, integers after normalization.
CREATE TABLE customers (
  customer_id TEXT PRIMARY KEY,
  email TEXT,
  marketing_consent,
  region TEXT,
  age INTEGER
);

    A table is not a file, and the database file is the wrong thing to hash. Two SQLite files holding identical rows can differ byte for byte: page layout, free pages and journal state all vary. The specification hashes exact bytes and leaves it to the producer to make serialization and row order deterministic, so this walkthrough defines one export and attests its output:

    SELECT json_group_array(json_object(
  'age', age,
  'customer_id', customer_id,
  'email', email,
  'marketing_consent', marketing_consent,
  'region', region
))
FROM (SELECT * FROM customers ORDER BY customer_id);

    The attested bytes are exactly what that query prints: one JSON array, rows ordered by customer_id, keys in alphabetical order, no whitespace, followed by a single line feed. sqlite3 customers.db < export.sql produces those bytes, so anyone with the sqlite3 shell can re-hash a state. The generator also serializes the rows independently and fails if the two ever disagree.

  3. Edit it in place

    Same table, same file. State 1 is gone from storage.

    One UPDATE normalizes every row where it sits: whitespace trimmed, email folded to lower case, consent resolved to 1 or 0, region upper-cased.

    UPDATE customers
SET email = lower(trim(email)),
    marketing_consent = CASE lower(trim(marketing_consent))
      WHEN 'yes' THEN 1 WHEN 'true' THEN 1 WHEN '1' THEN 1
      WHEN 'no' THEN 0 WHEN 'false' THEN 0 WHEN '0' THEN 0
    END,
    region = upper(region);

    A receiver holding the database and the three statements can re-run the export and compare it to statement 3's subject. It can hash each statement and follow the chain back to the origin. And for each step it can check that the input digest equals the previous statement's subject, which is what shows that nothing else wrote to the table between the two commands the statements describe.

    What it cannot do is re-hash state 1 or state 2 from the database. Makoto keeps the identity of every state, not its bytes. If the earlier rows must stay checkable, the exports have to be kept somewhere; this page publishes them alongside the statements for exactly that reason.

    As on the lifecycle page, these statements are unsigned, so they carry no authenticity or authorization claim, and nothing here anchors freshness. The runnable proof adds signatures, a receiver trust policy, and a pinned handoff.

Reproduce every digest on this page

State digests need only the sqlite3 shell and shasum. Start in an empty directory; the create command fails if customers.db already exists.

$ base=https://usemakoto.dev/examples/in-place/sql
$ for f in 00-create 01-load 02-normalize 03-withdraw-minor-consent export; do curl -fsSO "$base/$f.sql"; done
$ sqlite3 customers.db < 00-create.sql
$ sqlite3 customers.db < 01-load.sql
$ sqlite3 customers.db < export.sql | shasum -a 256

Statement digests are taken over the canonical serialization, keys sorted with no insignificant whitespace, not over the pretty-printed files:

python3 - <<'EOF'
import hashlib, json, urllib.request

BASE = "https://usemakoto.dev/examples/in-place/attestations/"
for name in ("state-1-origin", "state-2-normalize", "state-3-withdraw-minor-consent"):
    raw = urllib.request.urlopen(BASE + name + ".json").read()
    canonical = json.dumps(json.loads(raw), sort_keys=True, separators=(",", ":"))
    print(hashlib.sha256(canonical.encode()).hexdigest(), name)
EOF

That prints the three statement digests above, in order. From a checkout of this site, one command regenerates every export and statement, validates each statement against the schemas, and fails if a committed file has drifted:

$ uv run scripts/in_place_example.py --check

Two shapes, one rule: new bytes need a new statement.

The lifecycle walkthrough writes a new file at every step. This one rewrites a single table. Either way, each state gets its own digest and each statement names the one before it.
